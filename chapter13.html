Quantum Software Stack and Programming

A quantum computer is not simply a machine on which we run a quantum algorithm. Between the algorithm we write and the physical qubits that perform the computation, several layers of software must work together. This chapter explains how those layers fit together, how quantum programs are compiled and executed, and how to make their results reliable and reproducible.

13.1 Overview of the Quantum Software Stack: Algorithms to Hardware

13.1.1 Why does quantum computing need a software stack?

Imagine writing a program that sorts a list of numbers. You write instructions in a programming language, a compiler translates those instructions into operations that a processor understands, and the processor executes them using electronic circuits.

Quantum computing follows a similar idea, but the physical machine behaves differently. Instead of ordinary bits, it uses qubits. Instead of conventional logic gates alone, it uses quantum gates, which manipulate the state of qubits. Finally, measuring a qubit produces a classical result that we can read.

A quantum algorithm may describe an operation at a high level, but the actual device might support only a restricted collection of native gates. Its qubits may also have limited connectivity, different error rates and limited coherence times. Software must bridge the gap between the algorithm and these physical restrictions.

This collection of layers is called the quantum software stack. It converts a mathematical idea into operations that a real quantum processor can attempt to execute.

13.1.3 Application and problem definition

The first layer describes what we want to solve. For example, suppose we want to find the lowest energy of a small molecule, search for a marked item, or find a good solution to an optimisation problem.

At this level, the programmer thinks mainly about the problem rather than the physical quantum processor. A chemistry application might begin with a mathematical description of a molecule, while an optimisation application might begin with a cost function.

A quantum algorithm is selected according to the structure of the problem. Grover's algorithm, for example, is designed for unstructured search under a suitable oracle model. The Variational Quantum Eigensolver, or VQE, is commonly studied for estimating low-energy states of quantum systems.

Important distinction: choosing a quantum algorithm does not guarantee that a quantum computer will solve the problem faster than a classical computer. The input format, output requirements, noise, hardware scale and classical alternatives all matter.

13.1.4 Quantum circuit representation

Many quantum algorithms are expressed as quantum circuits. A circuit is a sequence of operations applied to qubits. Each operation changes the quantum state, and measurement converts information about that state into classical data.

For a simple example, consider two qubits initially in the state |00⟩. Applying a Hadamard gate to the first qubit and then a controlled-NOT gate, or CNOT, produces the Bell state

|Φ⁺⟩ = (|00⟩ + |11⟩) / √2

If both qubits are measured in the computational basis, the ideal outcomes are 00 and 11, each with probability one-half. This circuit is simple enough to describe mathematically, yet running it on real hardware still requires compilation, device execution and measurement processing.

13.1.5 Compilation and hardware execution

A high-level circuit may use convenient gates such as Hadamard, controlled-NOT and arbitrary rotations. A physical device may implement only a particular native gate set efficiently. The compiler rewrites the circuit into operations supported by the target device.

If two logical qubits need to interact but their physical counterparts are not connected directly, the compiler may insert SWAP gates or choose another mapping. These transformations make the circuit executable, but they can increase its size and expose it to additional errors.

The device then performs the compiled operations, measures selected qubits and returns classical results. A classical program processes those results, estimates probabilities or expectation values, and may decide what circuit to run next.

13.1.6 The classical computer remains essential

Quantum computers do not replace classical computers. Classical machines prepare inputs, construct circuits, optimise parameters, submit jobs, analyse measurements and store results.

In a hybrid algorithm such as VQE, the classical computer proposes parameters for a quantum circuit. The quantum processor estimates the energy associated with those parameters. The classical optimiser then uses the estimate to select new parameters. This cycle repeats until a stopping condition is reached.

Classical Optimiser Chooses Parameters
↓
Quantum Circuit Runs on a Simulator or QPU
↓
Measurements Estimate the Cost Function
↓
Classical Optimiser Updates Parameters
↺ Repeat until the stopping condition is met

A QPU, or quantum processing unit, is the processor that operates on qubits. The complete hybrid application may run mostly on a classical computer, with the QPU performing particular quantum operations.

13.2 Quantum Programming Frameworks

13.2.1 What is a quantum programming framework?

A quantum programming framework provides software tools for describing, transforming, simulating or executing quantum programs. It may provide circuit-building functions, mathematical operations, optimisers, simulators, visualisation and access to hardware providers.

Think of a framework as a workshop. It supplies the tools needed to construct a quantum circuit, inspect it, test it and prepare it for execution. Different workshops may use different programming languages and have different strengths.

There is no single framework that is best for every task. The right choice depends on whether we want to learn circuit basics, study quantum algorithms, differentiate quantum circuits, build a cloud application or experiment with a particular hardware platform.

13.2.2 Qiskit

Qiskit is an open-source quantum computing software ecosystem associated with IBM Quantum. Its circuit tools are widely used for creating quantum circuits, transforming them for different devices, running simulations and submitting supported workloads to quantum hardware.

Qiskit is particularly useful for learning how circuits are represented and how hardware constraints affect execution. It also provides transpilation tools that can translate a circuit into a form suitable for a target backend.

Python is commonly used to construct circuits with Qiskit. The following example creates a Bell-state circuit using the modern Qiskit circuit interface. 

from qiskit import QuantumCircuit

# Create two qubits and two classical bits.
qc = QuantumCircuit(2, 2)

# Put the first qubit into an equal superposition.
qc.h(0)

# Entangle the two qubits.
qc.cx(0, 1)

# Measure both qubits.
qc.measure([0, 1], [0, 1])

print(qc.draw())

The first line inside the circuit applies a Hadamard gate. The CNOT then entangles the qubits, and the final instruction records their measurement results in classical bits. This code constructs the circuit; it does not, by itself, guarantee execution on a real quantum processor.

13.2.3 Cirq

Cirq is an open-source Python framework developed by Google for constructing, transforming and executing quantum circuits. It provides explicit representations of qubits, operations, moments and circuits.

A moment represents operations that occupy the same logical time step, subject to the framework's operation compatibility rules. This makes Cirq useful for examining the arrangement and scheduling of circuit operations.

Cirq can be used with simulators and supported hardware integrations. It is especially useful for circuit-level experimentation, research and understanding how circuit structure affects execution. 

import cirq

# Create two qubits.
q0, q1 = cirq.LineQubit.range(2)

# Build a Bell-state circuit.
circuit = cirq.Circuit(
    cirq.H(q0),
    cirq.CNOT(q0, q1),
    cirq.measure(q0, q1, key="result")
)

print(circuit)

This example constructs a circuit and adds a measurement. To obtain measurement samples, we would run it using a simulator or an appropriate backend.

13.2.4 PennyLane

PennyLane is an open-source framework focused on quantum programming, differentiable quantum circuits and hybrid quantum-classical machine learning. It connects quantum operations with classical numerical and machine-learning tools.

One of its important ideas is the quantum node, often called a QNode. A QNode connects a quantum function to a device, such as a simulator or a supported quantum processor. Depending on the device and operations, the resulting computation can be integrated with classical automatic differentiation.

This is useful for variational circuits, quantum machine learning and optimisation problems where circuit parameters are updated using a classical learning procedure. 

import pennylane as qml
from pennylane import numpy as np

dev = qml.device("default.qubit", wires=1)

@qml.qnode(dev)
def circuit(theta):
    qml.RY(theta, wires=0)
    return qml.expval(qml.PauliZ(0))

theta = np.array(0.5, requires_grad=True)

value = circuit(theta)
gradient = qml.grad(circuit)(theta)

print("Expectation value:", value)
print("Gradient:", gradient)

The circuit rotates one qubit around the Y axis and measures the expectation value of the Pauli-Z operator. The framework can calculate the derivative with respect to the rotation parameter using a supported differentiation method.

The device name and API shown in examples depend on the installed PennyLane version. Real-device execution requires a compatible plugin, credentials and an appropriate backend.

13.2.5 Q#

Q# is a programming language designed for quantum computing. It provides language features for expressing quantum operations and classical control around quantum computation.

Unlike a circuit library that is simply imported into ordinary Python code, Q# has its own syntax and programming model. A quantum operation can allocate qubits, apply gates, measure them and return classical information.

Q# is useful when learning to express quantum programs in a language designed specifically for the task. Its development and execution tools have evolved over time, so the available workflow depends on the current Azure Quantum and QDK tooling. 

namespace BellExample {
    open Microsoft.Quantum.Intrinsic;
    open Microsoft.Quantum.Measurement;

    @EntryPoint()
    operation Main() : Result[] {
        use qs = Qubit[2];

        H(qs[0]);
        CNOT(qs[0], qs[1]);

        let results = [
            M(qs[0]),
            M(qs[1])
        ];

        ResetAll(qs);
        return results;
    }
}

This example illustrates the language structure used to allocate two qubits, create entanglement, measure them and reset the qubits before leaving the operation. Exact project configuration and command-line execution depend on the installed QDK version.

13.2.6 Amazon Braket

Amazon Braket is an AWS service for developing and running quantum computing workloads. It provides access to supported quantum computing hardware providers and managed simulation options through a cloud-based workflow.

Braket includes the Amazon Braket SDK, which supports circuit construction, simulator execution and submission of tasks to compatible devices. It is useful when quantum workloads need to fit into an AWS environment involving cloud permissions, storage, monitoring and classical processing.

A quantum task is a unit of work submitted to a device. A hybrid job can coordinate classical processing and quantum tasks. Availability, device restrictions, cost and supported features vary by provider and device. 

from braket.circuits import Circuit
from braket.devices import LocalSimulator

# Construct a Bell-state circuit.
bell = Circuit().h(0).cnot(0, 1)

# Run locally with a simulator.
device = LocalSimulator()
task = device.run(bell, shots=1000)

result = task.result()

print(result.measurement_counts)

This example uses a local simulator rather than a remote QPU. A hardware workflow would select a supported device, configure the required access and submit the task through the cloud service.

13.3 Transpilation, Compilation and Qubit Routing

13.3.1 Why can we not run every circuit directly?

A programmer may create a circuit using convenient operations without considering the physical arrangement of the qubits. A real processor, however, supports only particular operations and interaction patterns.

For example, a circuit may ask qubits 0 and 4 to interact using a two-qubit gate. On a particular processor, those physical qubits may not have a direct connection. Another device may not support the exact gate used in the original circuit.

The compilation process transforms a circuit so that it is compatible with the target system. It may decompose gates, choose physical qubits, insert routing operations, optimise gate sequences and schedule operations.

13.3.2 Compilation and transpilation

In classical computing, compilation generally translates a program into a representation that can be executed by a processor or runtime. Quantum computing uses a similar idea, although its compilation pipeline has additional challenges related to qubit connectivity, quantum state preservation and measurement.

Transpilation commonly refers to transforming a quantum circuit into another circuit that is more suitable for a target gate set, connectivity graph or backend. In some software ecosystems, transpilation is one stage of a broader compilation pipeline.

The precise terminology differs between frameworks. The essential idea is the same: convert a circuit from a convenient representation into one the selected device can execute.

13.3.3 The main stages of a quantum compilation pipeline

Stage 1: Circuit validation

The compiler checks whether the circuit is valid, whether its operations are supported by the selected workflow, and whether measurements and classical dependencies are represented correctly.

Stage 2: Gate decomposition

A high-level gate may be replaced with a sequence of lower-level gates. For instance, a device might implement a particular rotation directly but require a controlled operation to be expressed using several native operations.

The resulting circuit should preserve the intended mathematical operation, apart from any explicitly accepted approximation.

Stage 3: Initial qubit placement

The compiler assigns logical qubits to physical qubits. Logical qubits are the qubits used in the program's description. Physical qubits are the actual controllable units in the processor.

The compiler may consider connectivity, error estimates, calibration data and the interactions required by the circuit.

Stage 4: Routing

If an operation requires qubits that are not directly connected, the compiler finds a way to move their logical states through the hardware connectivity graph. This frequently involves SWAP gates or alternative decompositions.

Stage 5: Optimisation

The compiler may cancel adjacent inverse gates, combine compatible operations, reduce unnecessary gate counts or choose a more efficient decomposition.

Optimisation objectives can include circuit depth, gate count, expected error, execution time and hardware constraints. Improving one objective does not always improve all the others.

Stage 6: Scheduling and execution preparation

Operations are arranged into a valid execution schedule. The hardware interface may then prepare the instructions needed for control electronics, measurements and data collection. Some systems also expose pulse-level control to advanced users.

13.3.4 Logical qubits and physical qubits

A logical qubit is a position in the program's abstract circuit. A physical qubit is a device component used to implement that position.

Consider a circuit with three logical qubits, labelled A, B and C. The device might initially assign them to physical qubits 2, 5 and 7. This assignment is called a qubit mapping. Another mapping may produce a circuit that requires fewer routing operations or uses better-calibrated physical qubits.

In ordinary circuit compilation, logical qubits are often mapped to physical qubits without encoding each logical qubit into an error-corrected block. In fault-tolerant quantum computing, the term logical qubit can instead refer to a protected quantum information unit encoded across multiple physical qubits. These are related but distinct uses of the term.

13.3.5 Qubit connectivity as a graph

A processor's connectivity can be represented by a graph. Each vertex represents a physical qubit, and each edge represents an allowed direct interaction under the device's connectivity model.

In this example, Q0 can interact directly with Q1, and Q1 can interact directly with Q2. But Q0 and Q3 are not direct neighbours. A circuit that needs a two-qubit operation between Q0 and Q3 must be transformed to respect the available connectivity, unless the device offers another supported mechanism for that interaction.

13.3.6 How does a SWAP gate help?

A SWAP gate exchanges the quantum states of two qubits. It is commonly implemented using three CNOT gates when CNOT is the chosen two-qubit primitive.

SWAP(A, B) = CNOT(A, B) · CNOT(B, A) · CNOT(A, B)

The expression indicates a sequence of three operations; when reading the sequence as circuit instructions, operations are applied in the order specified by the circuit. Matrix multiplication conventions may display the written product in the reverse order.

Suppose logical qubit A is located at physical Q0 and logical qubit C is at Q3 in a linear device. The compiler may insert SWAP operations along the path so that the states move closer together. It can then perform the required interaction once the logical qubits occupy compatible locations.

A SWAP is not free. It consumes operations and execution time, and every additional operation can introduce errors. This is why qubit routing is an important part of quantum compilation.

13.3.7 Circuit depth and gate count

Two useful measures of a circuit are its gate count and circuit depth.

  • Gate count: the total number of operations represented in the circuit under the counting convention being used.
  • Circuit depth: the number of sequential operation layers required when compatible operations can be performed in parallel.

A circuit with many gates may have modest depth if numerous gates can run in parallel. Another circuit with fewer gates may have greater depth if its operations depend on one another. Actual execution time also depends on gate durations, scheduling, measurement and control-system overhead.

For noisy hardware, reducing unnecessary two-qubit gates and depth can improve the chance of obtaining useful results. However, an aggressively optimised circuit is not necessarily the best circuit for every device. Calibration data and compiler choices can affect the outcome.

13.3.8 Example of transpilation with Qiskit

from qiskit import QuantumCircuit, transpile
from qiskit_aer import AerSimulator

qc = QuantumCircuit(2)
qc.h(0)
qc.cx(0, 1)
qc.measure_all()

simulator = AerSimulator()

# Translate the circuit for the selected backend.
compiled = transpile(
    qc,
    simulator,
    optimization_level=2
)

print("Original circuit:")
print(qc.draw())

print("Compiled circuit:")
print(compiled.draw())

print("Compiled depth:", compiled.depth())
print("Compiled operations:", compiled.count_ops())

This example illustrates backend-aware transpilation and inspection of the resulting circuit. The simulator may accept operations that a particular physical device does not. For real hardware, transpilation should target the actual backend so that its basis gates and connectivity can be considered.

Remember: compilation does not remove the laws of quantum mechanics or make a noisy processor perfect. It transforms the circuit to make it executable and may improve efficiency, but hardware errors remain.

13.4 Quantum Simulators: Statevector, Density Matrix and Tensor Networks

13.4.1 Why do we need quantum simulators?

Before sending a circuit to a real quantum processor, it is useful to test whether the circuit behaves as expected. Quantum simulators do this using classical computing resources. They calculate the behaviour of a mathematical model of a quantum system rather than physically manipulating qubits.

Simulators help developers find mistakes, study measurement probabilities, test algorithms and compare different circuit designs. They are also important in research because experiments on real devices may be expensive, slow or affected by noise.

The main difficulty is that a general quantum state can require a large amount of classical memory to represent. A simulator may work beautifully for a small circuit but become impractical as the number of qubits or the complexity of the state grows.

13.4.2 Statevector simulation

A pure state of n qubits can be written as a superposition of all computational basis states:

|ψ⟩ = Σx=02ⁿ−1 αx|x⟩

Each amplitude α describes the complex probability amplitude associated with one basis state. The squared magnitude of an amplitude gives the probability of observing that basis state when measuring all qubits in the computational basis.

P(x) = |αx|²

A statevector simulator stores the amplitudes of a pure quantum state. Since an n-qubit state has 2ⁿ complex amplitudes in the general case, memory grows exponentially with the number of qubits.

If each complex amplitude uses 16 bytes, as with two 64-bit floating-point numbers, the amplitudes alone require approximately 16 × 2ⁿ bytes. At 30 qubits, this is roughly 16 GiB, before accounting for other memory needs. Actual requirements depend on the simulator's data types and implementation.

Number of qubits Number of amplitudes Approximate amplitude memory at 16 bytes each
5 32 512 bytes
10 1,024 16 KiB
20 1,048,576 16 MiB
30 1,073,741,824 16 GiB
40 1,099,511,627,776 16 TiB

These figures describe storage for the full, general statevector using the stated precision. They are not universal limits. Special circuits, sparse representations, lower precision, distributed computing and alternative simulation methods can change what is feasible.

How does a statevector simulator execute a gate?

A quantum gate is represented by a mathematical transformation. For a gate U, the state changes from |ψ⟩ to U|ψ⟩. The simulator applies this transformation to the stored amplitudes.

For example, the Hadamard gate transforms |0⟩ into (|0⟩ + |1⟩)/√2. A simulator updates the statevector to represent the resulting amplitudes. If the qubit is measured, the simulator samples an outcome according to the corresponding probabilities.

A simulator can often calculate the exact ideal probabilities before sampling. A real device generally returns finite measurement data affected by noise and hardware imperfections.

13.4.3 Density-matrix simulation

A statevector is sufficient to represent a pure quantum state. But quantum systems can also be mixed, particularly when we describe uncertainty about the state or the effects of interactions with the environment.

Density matrices provide a general representation that includes pure and mixed states. The density matrix of a pure state can be written as

ρ = |ψ⟩⟨ψ|

A mixed state can be represented as a probabilistic mixture of states:

ρ = Σi pi|ψi⟩⟨ψi|

Here, the probabilities pi are non-negative and sum to one. The density matrix contains information about the populations and coherences of the represented state.

Density matrices are useful for modelling noise channels, decoherence and certain forms of measurement uncertainty. For example, a noise channel may describe how a qubit can lose energy or lose phase coherence while interacting with its environment.

Why does density-matrix simulation need more memory?

A general n-qubit density matrix has 2ⁿ rows and 2ⁿ columns. It therefore contains 4ⁿ complex entries in a straightforward representation. This makes a general density-matrix simulation much more expensive than a statevector simulation as the number of qubits increases.

Density-matrix simulation is valuable when noise is central to the question, but it is not always the most practical choice for large systems.

13.4.4 Tensor-network simulation

A tensor is a mathematical object that generalises numbers, vectors and matrices to multiple dimensions. Tensor-network methods represent a large quantum state or circuit using a collection of smaller tensors connected according to a chosen structure.

The advantage is that some quantum states have structure that can be represented efficiently in this form. Rather than storing every amplitude explicitly, a simulator can store a collection of tensors and contract them to calculate selected quantities.

This is particularly useful for certain low-entanglement states, structured circuits and circuits whose connectivity makes the tensor contractions manageable.

However, tensor networks are not a universal solution to exponential scaling. Highly entangled states and difficult circuit structures can require large bond dimensions or expensive contractions. The efficiency depends on the structure of the circuit, not merely on the number of qubits.

13.4.5 Comparing the simulation methods

Method Representation Strength Main limitation
Statevector Vector of 2ⁿ complex amplitudes Direct and efficient for many small pure-state circuits. Memory generally grows exponentially with qubit count.
Density matrix Matrix of 4ⁿ complex entries Represents mixed states and supports general noise modelling. Very high memory and computational requirements.
Tensor network Network of connected tensors Can exploit favourable state and circuit structure. Cost can rise sharply for difficult contractions or high entanglement.

13.4.6 Exact simulation versus sampling

A simulator may calculate an ideal probability distribution, or it may generate a finite number of samples from that distribution. These are different tasks.

Suppose the ideal probability of observing 0 is 0.7 and the probability of observing 1 is 0.3. An exact probability calculation gives those values directly. A run with 100 measurements might return 68 zeros and 32 ones. The measured frequencies need not equal the exact probabilities.

Increasing the number of shots generally reduces sampling uncertainty, but it does not remove systematic hardware errors or model errors.

13.4.7 Choosing the right simulator

  • Use a statevector simulator for small ideal circuits, gate debugging and exact pure-state calculations.
  • Use density-matrix simulation when mixed states or explicitly modelled noise are important and the system is small enough.
  • Consider tensor-network methods when the circuit has structure that the selected implementation can exploit.
  • Use a real device when the goal requires experimental measurements from physical quantum hardware.
A simulator can verify that a circuit is mathematically sensible under its model. It cannot automatically prove that the same circuit will perform well on a noisy physical processor.

13.5 Running on Real Hardware and Cloud Platforms

13.5.1 What is a quantum processing unit?

A quantum processing unit, or QPU, is a physical processor that controls and manipulates qubits. Depending on the technology, those qubits may be built using superconducting circuits, trapped ions, photons, neutral atoms or other physical systems.

These technologies differ in their operating conditions, gate implementations, connectivity, measurement methods and error characteristics. As a result, a circuit that performs well on one device may need substantial changes before it can run efficiently on another.

13.5.2 Why use cloud platforms?

Building and maintaining a quantum processor requires specialised hardware, control electronics, calibration and often demanding environmental conditions. Most programmers do not have a quantum processor sitting on their desk.

Cloud platforms allow users to submit quantum workloads through software interfaces. The provider manages access to the underlying hardware and returns the results to the user. The exact experience depends on the platform, account, selected device and available access programme.

This makes quantum experimentation accessible without requiring every researcher or developer to operate a physical processor. It does not mean that every device is free, immediately available or suitable for every circuit.

13.5.3 Common parts of a cloud execution workflow

Step 1: Select a device

Choose a simulator or a supported QPU. Consider the number of qubits, gate set, connectivity, calibration information, availability, pricing and access restrictions.

Step 2: Prepare the circuit

Construct the circuit using a compatible framework. Check that it contains the intended gates and measurement operations.

Step 3: Compile for the target

Translate the circuit for the chosen device, taking its supported operations and connectivity into account. Inspect the compiled circuit when the platform permits it.

Step 4: Submit a job or task

The framework sends the workload through the platform's interface. The request may enter a queue, depending on the device and service.

Step 5: Execute and collect measurements

The platform executes the circuit, collects measurement data and makes the results available. The returned data may include counts, bitstrings, expectation values or other supported result formats.

Step 6: Analyse the results

The classical application processes the results, estimates quantities of interest and determines whether additional circuit runs are needed.

13.5.4 Shots and measurement counts

Quantum measurements are probabilistic. To estimate the distribution of outcomes, a circuit is often executed repeatedly. Each repetition is called a shot.

Suppose a two-qubit Bell-state circuit ideally produces 00 and 11 with equal probability. After 1,000 shots, a real experiment might return 486 occurrences of 00, 493 occurrences of 11 and a small number of 01 or 10 outcomes. The exact counts depend on sampling and hardware errors; these numbers are illustrative rather than an experimental result.

A useful first check is whether the observed results broadly match the expected distribution. If unexpected outcomes occur, possible causes include gate errors, readout errors, circuit-construction mistakes or differences between the assumed model and the actual device.

13.5.5 Sampling uncertainty

Suppose a measurement outcome has probability p and the circuit is measured independently N times. The estimated probability is the number of occurrences divided by N. Its approximate standard error under ideal independent sampling is

Standard error ≈ √[p(1 − p) / N]

This relationship shows that statistical uncertainty usually decreases in proportion to 1/√N. To reduce the sampling error by roughly a factor of two, about four times as many shots are needed, assuming the same ideal sampling model.

More shots cost additional execution resources and do not automatically correct biased measurements or other systematic errors. Shot selection should reflect the accuracy required by the application.

13.5.6 A simple simulator execution example

Before using remote hardware, we can test a circuit with a local simulator. The following Qiskit example creates a Bell state, executes it repeatedly and displays the measurement counts. 

from qiskit import QuantumCircuit, transpile
from qiskit_aer import AerSimulator

qc = QuantumCircuit(2, 2)

qc.h(0)
qc.cx(0, 1)

qc.measure([0, 1], [0, 1])

simulator = AerSimulator()

compiled = transpile(qc, simulator)

job = simulator.run(compiled, shots=1000)
result = job.result()

counts = result.get_counts()
print(counts)

An ideal simulator should return predominantly 00 and 11, with their frequencies varying due to finite sampling. The precise display format and availability of simulator packages depend on the installed versions.

13.5.7 Moving from a simulator to a real QPU

The conceptual workflow is similar, but the execution target changes. A real-device run needs an appropriate provider, valid authentication, access to the selected backend and compliance with its supported circuit and job limits.

The provider's current documentation should be followed for authentication, device selection, compilation and submission. Avoid assuming that a simulator backend and a hardware backend expose exactly the same features or APIs.

Before spending resources on a QPU, it is sensible to run a small circuit, confirm that the expected measurements are being returned, inspect the compiled circuit and estimate the likely cost of repeated executions.

13.5.8 What can go wrong on real hardware?

  • Gate errors: the physical operation may not perfectly match the intended quantum gate.
  • Readout errors: the reported classical bit may differ from the qubit's state at measurement.
  • Decoherence: interactions with the environment can disturb quantum information.
  • Connectivity overhead: routing may require extra operations.
  • Queueing and execution limits: the requested job may be delayed or rejected under provider constraints.
  • Calibration drift: device performance can change over time.
  • Classical integration issues: credentials, network configuration, SDK versions or job settings may prevent successful submission.

These are reasons to test a circuit progressively rather than immediately sending a large experiment to hardware.

13.6 Reproducibility and Best Practices

13.6.1 What does reproducibility mean?

A result is reproducible when another person can understand how it was produced and repeat the procedure under the same or sufficiently similar conditions. In quantum computing, this requires more than sharing the circuit alone.

A circuit's observed behaviour may depend on the framework version, compiler settings, simulator method, random seed, number of shots, noise model, hardware backend and calibration conditions.

If these details are missing, two people can run what appears to be the same experiment and obtain different results without either person making a programming mistake.

13.6.2 Record the software environment

Libraries evolve. Function names, defaults, backend behaviour and supported devices may change between releases. Record the versions used in an experiment and, when possible, use a dependency lock file to recreate the environment. 

# Example: record installed Python packages
python --version
python -m pip freeze > requirements-lock.txt

# Later, recreate the environment in a suitable
# virtual environment:
python -m pip install -r requirements-lock.txt

A package list is helpful, but it is not a complete guarantee of reproducibility. The Python version, operating system, hardware dependencies and external services may also matter.

13.6.3 Preserve the circuit and compilation settings

Save the original circuit as well as the compiled circuit when possible. The original describes the intended computation; the compiled version shows how that computation was adapted to a particular backend.

Record the backend, compiler or transpiler version, optimisation settings, qubit mapping and relevant basis-gate or routing information. This is especially important when investigating differences between devices.

13.6.4 Record the simulator configuration

Statevector and density-matrix simulations may represent different physical assumptions. A noiseless statevector simulation should not be treated as equivalent to a noisy hardware experiment.

Record the simulator name, simulation method, noise model, number of shots, precision and any random seeds used. If a seed is supported, it can help reproduce pseudorandom sampling under the same software and execution conditions.

A fixed random seed does not guarantee identical results across every simulator, library version, parallel execution configuration or hardware backend. It controls only the randomness supported by the particular workflow.

13.6.5 Treat real hardware as an experiment

Physical devices can change between runs. Calibration, noise, device availability and queue conditions may differ. Therefore, record the execution date, backend identifier, job identifier, shot count and relevant calibration information whenever the platform makes them available.

If a result is important, consider repeating the experiment. Compare the results statistically instead of expecting every run to return exactly the same measurement counts.

13.6.6 Use a layered testing strategy

A useful quantum software workflow resembles testing in ordinary software engineering. Each layer should be checked before relying on the complete application.

Test 1: Mathematical expectations

Calculate what should happen for a small example. For a Bell-state circuit, the ideal computational-basis probabilities should assign one-half to 00 and one-half to 11.

Test 2: Circuit construction

Inspect the circuit diagram, gate order, qubit indices, measurement mapping and classical registers. A small indexing mistake can change the experiment.

Test 3: Ideal simulation

Compare the circuit against the expected mathematical behaviour using an ideal simulator. This helps separate programming mistakes from physical noise.

Test 4: Noisy simulation

Introduce a suitable noise model to investigate how errors may affect the result. A simulated noise model is only as useful as its assumptions and calibration.

Test 5: Small hardware experiment

Run a simple circuit on the selected QPU. Confirm that submission, measurement and result retrieval work before scaling up the workload.

Test 6: Statistical analysis

Compare observed frequencies or expectation values with the ideal prediction and any noise-model prediction. Consider uncertainty and systematic errors when drawing conclusions.

13.6.7 Be careful when comparing frameworks

Suppose a circuit produces different results in two frameworks. It is tempting to conclude that one framework is incorrect. But the difference may come from measurement conventions, qubit ordering, gate definitions, compilation, shot counts, simulator methods or noise settings.

A fair comparison should use the same mathematical circuit, equivalent gate conventions, the same measurement basis, comparable execution settings and clearly documented assumptions.

Bitstring ordering deserves particular attention. Different tools may display classical bits in different orders. A result shown as 01 in one representation can correspond to the same physical outcome represented differently in another. Verify the framework's bit-ordering convention before comparing output strings.

13.6.8 Maintain an experiment record

A simple experiment record might contain the following information:

  • Problem statement and algorithm used.
  • Original circuit and relevant source code.
  • Framework, SDK and Python versions.
  • Compilation settings and compiled circuit.
  • Simulator method and noise assumptions.
  • Backend and device identifier, where applicable.
  • Number of shots and random seeds, if supported.
  • Execution date, job identifier and calibration metadata, where available.
  • Raw measurement results and processed results.
  • Statistical uncertainty and known limitations.

Store raw data separately from processed data. If an analysis script changes later, retaining the original measurements allows the new analysis to be performed without repeating an expensive experiment.

13.6.9 Reproducibility and responsible claims

A successful quantum circuit execution is not, by itself, proof of a quantum advantage. To make a meaningful performance claim, one must define the task, compare against strong classical methods, account for data loading and result extraction, include relevant overheads and report uncertainty.

Likewise, a small demonstration that works on a simulator does not establish that the same method will scale to a useful problem on present-day hardware.

Good quantum software practice combines mathematical reasoning, careful implementation, appropriate simulation, transparent experiments and honest interpretation of results.

A Complete Practical Example: From Algorithm to Results

Step 1: Define the goal

We want to prepare a two-qubit Bell state and check whether measurements show the expected correlation. This is a small experiment, but it illustrates the entire software workflow.

Step 2: Write down the expected behaviour

Starting from |00⟩, apply a Hadamard gate to qubit 0 and a CNOT gate with qubit 0 as the control and qubit 1 as the target.

|00⟩ → (|00⟩ + |10⟩)/√2 → (|00⟩ + |11⟩)/√2

The ideal measurement probabilities are P(00) = 0.5, P(11) = 0.5, P(01) = 0 and P(10) = 0. These are predictions of the ideal circuit, not guaranteed frequencies from a finite experiment.

Step 3: Build the circuit

from qiskit import QuantumCircuit

qc = QuantumCircuit(2, 2)
qc.h(0)
qc.cx(0, 1)
qc.measure([0, 1], [0, 1])

print(qc.draw())

Step 4: Simulate it

from qiskit import transpile
from qiskit_aer import AerSimulator

simulator = AerSimulator()
compiled = transpile(qc, simulator)

job = simulator.run(compiled, shots=1000)
result = job.result()

counts = result.get_counts()
print(counts)

The counts should be dominated by 00 and 11 for an ideal simulation. Finite sampling can make the two counts unequal.

Step 5: Inspect the compiled circuit

Examine the compiled circuit and count its operations. For a simulator, the compiler may preserve or transform operations according to that simulator's supported gates. For a QPU, the result can differ according to the hardware target and its connectivity. 

print(compiled.draw())
print("Depth:", compiled.depth())
print("Operations:", compiled.count_ops())

Step 6: Execute on a QPU, if access is available

Select a compatible device through the platform's current workflow, transpile for that target, submit the circuit and collect its results. Keep the simulator output for comparison. Do not assume that the hardware result must exactly match the simulated counts.

Step 7: Analyse the results

Calculate the frequency of each outcome by dividing its count by the total number of shots. Compare those frequencies with the expected distribution. Record the device, software versions, compilation settings and job details so that the experiment can be understood later.

What have we learned? A quantum program begins with a mathematical goal, becomes a circuit, is transformed for a chosen execution target, runs on a simulator or physical processor, and finally produces classical data that must be analysed carefully.

Chapter Summary

The quantum software stack connects quantum algorithms to physical quantum hardware. Each layer solves a different problem, from describing the desired computation to transforming circuits and collecting measurement results.

  • The software stack links the application, algorithm, programming framework, compiler, hardware interface and result-processing stages.
  • Qiskit, Cirq, PennyLane and Q# provide different ways to express and work with quantum programs. Amazon Braket provides a cloud service for supported simulators and hardware.
  • Compilation and transpilation transform circuits to respect the target device's gate set, connectivity and other constraints.
  • Qubit routing handles interactions between logical qubits that may not be directly connected on the physical processor.
  • Statevector simulation represents pure states, while density-matrix simulation also represents mixed states. Tensor-network methods can exploit favourable circuit structure.
  • Cloud platforms allow users to submit quantum workloads without operating their own quantum processor.
  • Shots are repeated circuit executions used to estimate measurement distributions. More shots reduce sampling uncertainty but do not automatically eliminate hardware errors.
  • Reproducibility requires preserving code, versions, circuits, compiler settings, simulator assumptions, execution details and raw results.

The central idea

Quantum programming is not merely about applying quantum gates. It is about connecting mathematical algorithms, software representations, compilation, physical constraints and experimental evidence into one reliable workflow. A good quantum programmer understands not only what a circuit is supposed to do, but also how the software transforms it, how the hardware executes it and how the resulting data should be interpreted.
